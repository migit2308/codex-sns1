対象範囲と設計の前提

トップページSCR-001（URL：/）の投稿一覧ITEM-003を対象とする。FUN・PRG・PRC等のIDは本書で管理する設計上のID。各図は処理の設計案であり、実装済みであることを示さない。

閲覧処理は事前にシード投入した投稿の参照のみとし、DBへのINSERT・UPDATE・DELETEを行わない。投稿の作成・編集・削除は対象外。左右のサイドバー（COM-001・COM-002）の検索・通知・トレンド・おすすめなどは採用未決であり、本書では投稿一覧の処理に含めない。残る未決事項を14章にまとめる。

PRC-001：トップページの投稿一覧表示

設計項目 内容・決定状況
目的・関連 FUN-001 / PRG-001 / SCR-001（/）/ ITEM-003。取得結果を画面に表示する。
起動・入力 トップページへのアクセスを起点に、条件指定なしで一覧取得APIを呼び出す。認証なし。
出力 取得中・一覧あり・0件・取得失敗の表示状態と、成功時の投稿データ。表示文言は未決。
手順 ①取得中にする ②HTTP GETでPRC-002を呼び出す ③Postの配列を受け取る ④一覧あり・0件・失敗へ分岐する ⑤受信した順序のまま表示し、日時にはdisplayed_atを用いる。
副作用・例外 投稿データは更新しない。失敗を空一覧として扱わない。表示中の再取得・中断・古い応答の破棄は未決。

PRC-002：投稿一覧の取得・整形

設計項目 内容・決定状況
目的・関連 FUN-001 / PRG-002 / CLS-001。バックエンドAPIで投稿テーブルを全件参照し、Postの配列をJSONで返す。HTTPの仕様はAPI-001に従い、200・500ともCache-Control: no-storeを付ける。
入力・条件 絞り込みなしで投稿テーブルの全データを取得する。posted_at降順、同日時はpost_id降順。件数上限・ページネーション・追加読み込みは設けない。同じ投稿日時の場合はpost_idの降順とする。API認証は不要。
出力 正常：Postの8属性を持つJSONオブジェクトの配列（0件は[]）。各属性名と型は6章の属性一覧に一致させる。異常：取得失敗。APIの取得・変換失敗はHTTP 500、JSON形式でcode: POST_LIST_FETCH_FAILEDとmessage: 投稿一覧を取得できませんでした。を返す。
手順 ①投稿テーブルをposted_at降順、同日時はpost_id降順で全件SELECTする ②現在時刻を1回取得する ③各行のposted_atが現在時刻を超えないことを検証する（未来の行が1件でもあれば一覧全体をERR-001とする） ④各行からPostを生成し、posted_atと現在時刻からdisplayed_atを算出する ⑤Postの8属性を同名のJSON項目にして配列で返す。途中の失敗は異常として呼出元へ伝える。
整合性・資源 一覧取得はsns.dbのpostsを参照するのみ。要求ごとのセッションを取得・変換後に必ず閉じ、失敗時も解放する。タイムアウト・再試行は未決。
完了条件・確認観点 1件・複数件・0件で全件が返り、posted_at降順、同日時はpost_id降順であること。Postの8項目と型、0以上の各件数、長文・改行、DB停止・通信失敗・変換失敗を確認する。同一posted_atではpost_id降順、1週間以上の日本時間での日付境界、posted_at == nowの正常表示とposted_at > nowの一覧全体500を確認する。displayed_atは59秒/60秒、3599秒/3600秒、86399秒/86400秒、604799秒/604800秒の境界を確認する。

正常応答のデータ形式例

値はサンプル。現在時刻を2026-10-22T12:00:00+00:00とした例。Postの属性名をそのままJSONのキーにし、一覧用のラッパーや別の応答項目を追加しない。 

[
  {
    "post_id": 1,
    "author": "ユーザーA",
    "body": "トップページのレイアウトを考えています。",
    "posted_at": "2026-10-20T12:00:00+00:00",
    "reply_count": 2,
    "retweet_count": 1,
    "like_count": 5,
    "displayed_at": "2日"
  }
]

displayed_at：表示日時の算出

API処理で現在時刻nowを1回取得し、各Postについて 経過秒数 = now - posted_at を求める。DBのposted_atはUTCとして復元してから比較する。同じ応答内ではnowを共有し、時差を含む同じ時間軸で比較する。1日は24時間、1週間は7日（604800秒）とする。

経過時間 displayed_atの値 例
1分未満 たった今 0〜59秒 → たった今
1分以上・1時間未満 整数の分数 + 分（端数切り捨て） 120秒 → 2分
1時間以上・1日未満 整数の時間数 + 時間（端数切り捨て） 7200秒 → 2時間
1日以上・1週間未満 整数の日数 + 日（端数切り捨て） 172800秒 → 2日
1週間以上 投稿日時をAsia/Tokyoへ変換し、yyyy/mm/dd形式に整形 2026年10月1日の投稿 → 2026/10/01

算出したdisplayed_atは応答時の値とし、DBの更新は行わない。画面を開いたままの自動再計算は今回の対象外。日付表示はAsia/Tokyo（JST、UTC+09:00）とする。posted_atが現在時刻nowを超える行が1件でもあれば、ERR-001として一覧取得全体をHTTP 500・POST_LIST_FETCH_FAILEDにする。未来の行の除外や相対表示の補正は行わない。posted_at == nowは正常とする。投稿データのサンプル用SampleMessage・GreetingResponseはPostの正式な仕様に流用しない。

16. エラーコード一覧

分類：管理系

ERR IDは設計上の識別子。ERR-001のAPIエラーコードはPOST_LIST_FETCH_FAILED、HTTPステータスは500、返却JSONはcode・messageとする。準備処理のERR-002の終了コードは未決。HTTP応答を受け取れない通信失敗はAPIの500とは区別する。

エラーID 意味・発生条件 関連処理・ログ 表示・返却内容 再試行・復旧
ERR-001 一覧取得失敗：DB参照、API通信、Postの生成・JSON変換・表示日時算出の失敗。取得した投稿のposted_atが現在時刻nowを超える場合も対象とし、1件でも含まれれば一覧全体を失敗にする。 PRC-002→PRC-001 / LOG-001 APIの取得・変換失敗：HTTP 500、code: POST_LIST_FETCH_FAILED、message: 投稿一覧を取得できませんでした。を返す。内部例外・SQL・接続情報は返さない。フロントエンドは通信失敗も取得失敗として扱うが、サーバーの500応答と区別する。 再試行の条件・回数・操作は未決。DB復旧等の対応は原因別に定義する。
ERR-002 準備処理失敗：マイグレーション・確認データ投入の失敗。 PRC-003・PRC-004 / LOG-002 開発者向けの失敗通知。終了コード・詳細の形式は未決。 成功を前提に次の準備処理へ進めない。復旧・再実行方法はツールと投入方式の決定後に定義する。
対象外 取得成功かつ0件 PRC-002→PRC-001 エラーではなく、空の状態として表示する。 対象外
