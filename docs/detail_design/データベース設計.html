2. データベース設定

設計項目 内容・決定状況
製品・バージョン SQLite＋Python標準sqlite3＋SQLAlchemy。調査時のローカル実行環境はSQLite 3.50.4、SQLAlchemy 2.1.5。SQLiteはPythonの実行環境に依存するため実装時にも確認する。Alembic 1.20.1を導入済み。
構成・保存先 ローカルファイルDB：backend/data/sns.db。スキーマはmain。接続先はコード位置を基準に解決し、作業ディレクトリに依存させない。既存のbackend/data/sample.dbとは分離する。
文字コード・照合 新規DBはUTF-8、文字列比較は既定のBINARY。日本語のauthor・bodyを保存する。大文字小文字を無視する検索等は対象外。
日時と型の区別 通常の非STRICTテーブルを使用。SQLAlchemy型はDateTime(timezone=False)、DDLの宣言型はDATETIME、実際の保存クラスはTEXT。SQLiteには日時専用の保存型はない。宣言だけで日時の妥当性は保証されない。
UTCの保存・復元 投入時に時差付き日時をUTCへ変換し、その後tzinfoを外してSQLAlchemyへ渡す。保存文字列はYYYY-MM-DD HH:MM:SS.ffffff。読み取り時はUTCのtzinfoを付与してPostへ渡す。SQLAlchemyが自動でUTCへ変換するとは扱わない。
日本時間での表示 DBはUTCのまま。APIが経過時間を同じ時間軸で計算し、1週間以上はAsia/Tokyoでyyyy/mm/ddを作る。 算出ルール 参照。
日時検証 シードは実在する日時・時差情報・UTCへの変換可能性を検証する。未来日時は投入前に拒否する。既存DB等に未来のposted_atがあればAPIが検出し一覧全体をERR-001（HTTP 500・POST_LIST_FETCH_FAILED）とする。動的な現在時刻比較をDBのCHECKには入れない。
接続・権限 ローカルSQLiteにDB用パスワードは設けない。OSのファイル権限で管理し、DBを公開配信するディレクトリに置かない。APIの認証なしとDBファイルの公開は別に扱う。
セッション・資源 PRC-002は取得要求ごとにセッションを作成し、取得・変換後に必ず閉じる。失敗時もクローズする。PRC-004は1トランザクションで投入し、例外時はロールバックする。PRC-006は1投稿1トランザクションで、コミット前の失敗はロールバックし、成否にかかわらずセッションを閉じる。
SQLite設定・運用 初期構成は通常テーブル・既定のDELETEジャーナル方式。WAL等の追加設定は今回採用しない。準備処理はAPIを停止した状態で単独実行する。クライアントの5秒はサーバーのロールバック保証ではない。DBロック待機は既存ドライバーの設定を維持し、失敗はERR-004とする。本番運用・性能調整は未決。
投稿APIの接続（未実装） GETは既存mode=roを維持。POSTはSQLite URIのmode=rwで既存DBだけを開き、未作成ファイル・ディレクトリを自動生成しない。接続先のSNS_DATABASE_PATH解決は共通化する。未移行・書き込み不能はERR-004。準備用の接続・初期化と分離する。

根拠： SQLiteの日時保存形式 / SQLAlchemyのSQLite日時型 。

設計項目 内容・決定状況
文字列制約 半角スペースU+0020、全角スペースU+3000、タブU+0009、改行U+000A、復帰U+000D、垂直タブU+000B、改ページU+000Cのみで構成される値と空文字を禁止する。判定用にtrimした値を使用し、保存する本文・投稿者名はtrimしない。
アプリ側の同じ判定 author.strip(" \u3000\t\n\r\v\f")とbody.strip(" \u3000\t\n\r\v\f")が空でないことを検証する。具体的なコードではUnicode全角空白と各制御文字を使用する。
型変換への注意 SQLiteの型親和性により、例えば数値文字列が整数に変換されてからCHECKされる場合がある。シード入力のPython型も検証し、件数はboolを除くintかつ0以上とする。CHECKは保存後の型を保証する。
日時の制約範囲 DBはNOT NULLとTEXT保存を検証する。日時書式・実在日付・UTC統一・未来日時の検証はアプリ側で行う。不正文字列もDATETIME宣言だけでは防げない。
保持・削除 今回は論理削除列・編集日時列を追加しない。通常の閲覧とシード再実行では既存行を削除・更新しない。保持期間・削除運用は未決。

DDL案（通常のSQLiteテーブル）

下記は設計内容を確認するSQL案。実装ではAlembicから同等のテーブル・制約・インデックスを作成する。 

CREATE TABLE posts (
    post_id INTEGER PRIMARY KEY AUTOINCREMENT,
    author TEXT NOT NULL,
    body TEXT NOT NULL,
    posted_at DATETIME NOT NULL,
    reply_count INTEGER NOT NULL DEFAULT 0,
    retweet_count INTEGER NOT NULL DEFAULT 0,
    like_count INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT ck_posts_author_not_blank CHECK (typeof(author) = 'text' AND length(trim(author, char(32) || char(12288) || char(9) || char(10) || char(13) || char(11) || char(12))) > 0),
    CONSTRAINT ck_posts_body_not_blank CHECK (typeof(body) = 'text' AND length(trim(body, char(32) || char(12288) || char(9) || char(10) || char(13) || char(11) || char(12))) > 0),
    CONSTRAINT ck_posts_posted_at_text CHECK (typeof(posted_at) = 'text'),
    CONSTRAINT ck_posts_reply_count_nonnegative CHECK (typeof(reply_count) = 'integer' AND reply_count >= 0),
    CONSTRAINT ck_posts_retweet_count_nonnegative CHECK (typeof(retweet_count) = 'integer' AND retweet_count >= 0),
    CONSTRAINT ck_posts_like_count_nonnegative CHECK (typeof(like_count) = 'integer' AND like_count >= 0)
);
CREATE INDEX ix_posts_posted_at_post_id
    ON posts (posted_at DESC, post_id DESC);

PRC-003：Alembicによる変更履歴管理

設計項目 内容・決定状況
適用対象 sns.dbだけを対象とし、既存のsample.dbに接続・適用しない。Alembicの接続先とAPI・シードの接続先を統一する。
初回リビジョン AUTOINCREMENT付きのposts、名前付きCHECK制約、IDX-001を作成する。sqlite_sequenceはSQLiteが自動生成・管理するため、移行スクリプトで手動作成・更新しない。適用履歴はAlembicがalembic_versionで管理する。create_allで履歴管理を代替しない。
適用手順 開発者がAPI停止を確認→対象DBと現行リビジョンを確認→Alembic upgrade headを実行→テーブル・インデックス・headを確認→シードを投入する。既にheadなら再適用による変更はない。
失敗・再実行 SQLiteのDDLが常に一括ロールバックできるとは仮定しない。エラーでシードへ進まず、スキーマと適用履歴を確認して不整合を解消してから再実行する。詳細は実装時の初回リビジョンで検証する。
取り消し 初回リビジョンのdowngradeはインデックス・postsを削除し投稿を失うため、通常の再実行・復旧手順では実行しない。必要時は明示的な判断とバックアップを伴う。
実装時の確認 空のDBへの適用、headでの再実行、既存シードの保持、途中失敗時の履歴とスキーマを検証する。backend/alembic.ini、backend/migrations、backend/src/snsに実装済み。

設計項目 内容・決定状況
実行条件 開発者がマイグレーション完了後に明示実行する。APIから自動で呼ばない。投入先はsns.db。

失敗時の処理 参照・変換・未来日時検出の失敗は既存のERR-001に従う。準備処理の失敗はERR-002として作業を中止する。DBがない場合に閲覧APIが空DBを新設して正常0件と扱わないよう、読み取り専用接続mode=roで未作成ファイルを作らず、未移行スキーマも取得失敗として扱う。
ジャーナル・整合性 SQLite管理の付随ファイルを使用中に削除・変更しない。DB稼働中の単純なファイルコピーを整合性のあるバックアップとみなさない。バックアップ・復元方式は運用設計で決定する。
ログ・監視 投稿本文・接続情報はログに出さない。LOG-001はPRC-002、LOG-003はPRC-006と例外種別を標準エラーに出力する。シードは成功・失敗をコンソールに通知する。ログ保持期間、監視、バックアップ周期・世代は未決。
実装後に測定すること DBファイルサイズ、インデックス等の使用ページ数、ジャーナルのピーク容量、取得時間。今回の文書編集では未測定。
