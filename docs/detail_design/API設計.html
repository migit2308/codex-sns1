対象と設計の前提

API-001（投稿一覧取得）は実装済み。Issue #3のAPI-002（投稿作成）は設計確定・実装済み。投稿の編集・削除、件数を増減する操作、投稿ボタン以外のサイドバー機能は対象外。

2. 共通仕様

設計項目 仕様
環境・ベースURL 開発時のブラウザ：http://127.0.0.1:5173。フロントエンドは相対パス /api/posts または /api/posts/{post_id} を呼び出す。バックエンドへの直接アクセス：http://127.0.0.1:8000/posts（一覧・作成）、http://127.0.0.1:8000/posts/{post_id}（詳細）。本番の配信URL・転送構成は未決。
転送経路 既存のfrontend/vite.config.jsの設定に従い、Viteが /api を取り除いてバックエンドへ転送する。GET /api/posts → GET /posts、POST /api/posts → POST /posts。詳細はGET /api/posts/{post_id} → GET /posts/{post_id}。画面URL /・/posts/{post_id}とは区別する。
バージョン・命名 本文書は1.3.0。URLにはバージョン番号を付けない。JSONのキーはPostの属性と同じlower_snake_caseとする。
通信・データ形式 GET・POST。正常・エラーともJSON（UTF-8）、Content-Type: application/json。GETはボディなし。POSTはContent-Type: application/jsonでJSONオブジェクトを送る。
ヘッダー・キャッシュ Accept: application/json。API-001の200・500、API-002の201・422・500、API-003の200・404・422・500にCache-Control: no-storeを付与する。
認証・認可 認証なし。Authorizationヘッダーやログイン状態を取得条件にしない。今回の閲覧処理に認証由来の401・403は定義しない。
日時・数値・ID post_idと各件数はJSONの数値（整数）。件数は0以上。posted_atは時差情報付きISO 8601文字列。displayed_atはAPI-001（一覧）のGET応答のみの計算済み表示文字列。日本国内向けとし、日付表示はAsia/Tokyo（JST、UTC+09:00）を使用する。
必須・null・空文字 一覧GETの各投稿は8項目、POSTの作成結果と詳細GETはdisplayed_atを除く7項目が必須・null不可。author・bodyはDBで空文字と指定した空白だけの値を禁止する。DBと一覧・詳細応答には文字数上限を追加しない。新規作成リクエストにはAPI-002の280コードポイント制限を適用する。空白の定義とシード時の検証はDB設計TBL-001に従い、APIは保存された文字列を返す。
取得範囲・並び順 API-001は投稿テーブルの全件をposted_at降順、同日時はpost_id降順で取得する。フィルター・limit・offset・カーソル・ページネーション・追加読み込みは定義しない。API-003はpost_idの一致する1件のみを取得する。
入力検証 API-001には入力項目なし。未定義クエリは従来どおり無視する。API-002は必須の文字列bodyのみを受け付け、入力不正はERR-003とする。API-003はpost_idの整数・1以上を検証し、422は標準detail配列とする。余分なJSON項目・型変換は許可しない。
副作用・重複呼出・制限 GETは参照のみ。POSTは1件を追加し、呼び出すたびに別投稿となる。冪等キー・サーバー側の再送信重複防止・レート制限は未採用。クライアントは送信中の連打を抑止し、GET・POSTとも5秒の期限、自動再試行なし。
ブラウザからの呼び出し 開発環境では同一オリジンの /api/posts または /api/posts/{post_id} をVite経由で呼ぶ。ブラウザから別オリジンのバックエンドへ直接接続する方式や追加CORS設定は今回採用しない。本番の構成は未決。
互換性 応答のラッパーは追加しない。属性・型を変更する場合はAPI・ロジック・入出力設計の対応箇所とJSON例を同時に更新する。今後の互換性維持・バージョン移行方針は未決。

API-001：投稿一覧取得

設計項目 仕様
目的・関連 SCR-001（/）のITEM-003に表示する投稿を返す。内部処理はPRC-002、返却データはPost（CLS-001）。
メソッド・パス ブラウザ：GET /api/posts。バックエンド：GET /posts。認証なし。
共通仕様との差分 なし。2章の仕様を適用する。

リクエスト

区分 項目 必須・形式 仕様
パス変数 なし 対象外 全投稿が対象。
クエリ なし 対象外 条件指定なし。
ヘッダー Accept 任意・application/json JSON応答を受け取る。Authorizationは不要。

成功レスポンス

設計項目 仕様
HTTPステータス 200 OK。0件でも200とする。204や404にはしない。
ヘッダー Content-Type: application/json
Cache-Control: no-store
ボディ Postの8属性を持つオブジェクトの配列。items・data・totalなどのラッパーや付加項目は設けない。全件をposted_at降順、同日時はpost_id降順で返し、0件なら[]。
項目名 JSONの型 必須・null 内容 サンプル値
post_id number（整数） 必須・null不可 投稿1件の識別子。 1
author string 必須・null不可 投稿者の表示名。関連Userオブジェクトを含めない。 ユーザーA
body string 必須・null不可 投稿本文。改行はJSON文字列内で表現する。 サンプルの投稿です。
posted_at string（ISO 8601） 必須・null不可 投稿日時。UTCのZまたは時差オフセットを持つ。クラスではdatetime。 2026-10-20T12:00:00+00:00
reply_count number（整数） 必須・null不可 リプライ数。0以上の保存値。 2
retweet_count number（整数） 必須・null不可 リツイート数。0以上の保存値。 1
like_count number（整数） 必須・null不可 いいね数。0以上の保存値。 5
displayed_at string 必須・null不可 posted_atと応答処理時の現在時刻からAPIが算出する。DBには保存しない。 2日

属性の元定義は 6章のPost属性一覧 を参照する。displayed_atは 14章の算出ルール に従い、1分未満は「たった今」、1時間未満は「○分」、1日未満は「○時間」、1週間未満は「○日」、1週間以上は「yyyy/mm/dd」とする。同じ応答では現在時刻を1回取得して全投稿に使用する。1週間以上の場合はposted_atをAsia/Tokyoへ変換してyyyy/mm/ddに整形する。

取得失敗

DB参照・Post生成・表示日時算出・JSON変換の失敗、および未来のposted_atの検出は、 ERR-001 に対応するHTTP 500を返す。途中まで生成した一覧を成功応答として返さず、空配列にも置き換えない。

取得した投稿にposted_at > nowの行が1件でもあれば、一覧取得全体をHTTP 500・POST_LIST_FETCH_FAILEDとする。未来の投稿を除外した部分一覧を返したり、「たった今」に補正したりしない。posted_at == nowは正常とし「たった今」を返す。日時の比較は時差を考慮した同じ時間軸で行う。

副作用と失敗時の状態

取得の成功・失敗のどちらもDBの投稿や件数を変更しない。通信断などで応答を受け取れなかった場合、クライアントは取得失敗として扱うが、APIの500応答を受信したとはみなさない。画面の状態管理・復旧導線は入出力・ロジック設計を参照する。

確認観点（自動テスト・画面操作で確認）

追加確認：同一posted_atの投稿を複数用意しpost_idの大きい順となること。1週間以上前の2026-10-01T18:00:00+00:00は日本時間で2026/10/02と表示されること。posted_atがnowと等しい場合は正常、わずかでも未来なら一覧全体が500となることを確認する。

API-002：投稿作成（設計確定・実装済み）

設計項目 仕様
関連・状態 SCR-002 / FUN-003 / PRC-006。設計確定・実装済み。
経路 POST /api/posts → Vite → POST /posts。認証なし。
パス・クエリ パス変数・クエリの定義なし。未定義クエリは無視し、クライアントは送信しない。
ヘッダー Content-Type: application/json（必須）。Accept: application/json（任意）。Authorization不要。
body JSONオブジェクト内のbodyだけを必須のstringとして受け付ける。既定値なし・null不可。1〜280 Unicodeコードポイント。空欄・指定空白のみ・型違い・余分な項目・不正JSONは422。
文字列規約 改行・前後の空白を保持し、trim・Unicode正規化をしない。空白判定の文字はU+0020（半角スペース）、U+3000（全角スペース）、U+0009（タブ）、U+000A（改行）、U+000D（復帰）、U+000B（垂直タブ）、U+000C（改ページ）。コードポイント数はPythonのlenで数え、結合絵文字は複数として数える。
201 Created CreatedPost（CLS-003）の7項目を持つ単一オブジェクト。ラッパーなし。全項目必須・null不可。post_idはDB採番、authorは「自分」、bodyは受信値、posted_atは検証直後に1回取得した受付時刻（UTC）、各件数は0。displayed_atは返さず算出もしない。ホームの一覧反映時は画面側で「たった今」を補い、一覧GETの再取得後はAPI-001の表示日時を使用する。詳細からの投稿成功後も既存の詳細表示を維持する。
応答ヘッダー 201・422・500ともContent-Type: application/json、Cache-Control: no-store。
副作用・トランザクション 1要求1投稿。入力不正ではDB操作なし。応答生成・JSONシリアライズの検証をコミット前に完了し、コミット完了後のみ201を送る。内部手順はPRC-006。
再送信・結果不明 通信断・5秒の期限超過・不正応答ではコミット済みの場合がある。クライアントの中断はDBの取消を保証しない。本文を保持し一覧確認を促す。自動再送信・サーバー側の重複防止なし。

ケース 期待結果

500 {"code":"POST_DETAIL_FETCH_FAILED","message":"投稿詳細を取得できませんでした。"}。DB接続・参照・型検証・未来日時・JSON変換の失敗。 原因解消後に手動で再試行。内部情報は返さない。

200・404・422・500すべてにCache-Control: no-storeを付与する。422はPOSTの独自エラー変換の対象に含めず、本文は標準形式のままヘッダーを付与する。

4. エラー仕様

API-001の取得失敗、API-002の入力不正・保存失敗、API-003の対象なし・取得失敗はcode・message形式。内部例外・SQL・接続情報は含めない。API-003の422だけはFastAPI標準のdetail配列とし、POSTの422変換とは区別する。追跡IDは今回採用しない。

応答項目 型 必須・null 値・意味
code string 必須・null不可 エラー一覧で定義する固定コード（POST_LIST_FETCH_FAILED、POST_VALIDATION_FAILED、POST_CREATE_FAILED、POST_NOT_FOUND、POST_DETAIL_FETCH_FAILED）。
message string 必須・null不可 エラー一覧で定義する利用者向けの固定文言。

500 Internal Server Error。Content-Type: application/json、Cache-Control: no-store。

}

HTTP通信失敗など、レスポンス自体を受信できない場合はこのJSONを受け取れる保証はない。クライアント側の通信失敗と、サーバーが返したERR-001を区別する。
