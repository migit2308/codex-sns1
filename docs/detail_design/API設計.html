対象と設計の前提

対象はAPI-001（投稿一覧取得）のみ。開発者が事前にシード投入した投稿を取得・表示するための仕様で、APIは実装済み。投稿の作成・編集・削除、件数を増減する操作、サイドバー内の機能は本書の対象外。

項目名・型はPost（CLS-001）に合わせる。API設計ではHTTPで受け渡す形式を記載し、表示日時の計算手順はロジック設計、テーブルの物理構造はDB設計で管理する。

関連設計書： 入出力設計：SCR-001 / ロジック設計：PRC-002 / Post：CLS-001 / データベース設計

2. 共通仕様

設計項目 仕様
環境・ベースURL 開発時のブラウザ：http://127.0.0.1:5173。フロントエンドは相対パス /api/posts を呼び出す。バックエンドへの直接アクセス：http://127.0.0.1:8000/posts。本番の配信URL・転送構成は未決。
転送経路 既存のfrontend/vite.config.jsの設定に従い、Viteが /api を取り除いてバックエンドへ転送する。GET /api/posts → GET /posts。フロントエンドのトップページURL /とは区別する。
バージョン・命名 本文書は1.0.0。URLにはバージョン番号を付けない。JSONのキーはPostの属性と同じlower_snake_caseとする。
通信・データ形式 HTTP GET。正常・サーバーエラーともJSON（UTF-8）。レスポンスのContent-Typeはapplication/json。リクエストボディを持たないため、リクエストのContent-Type指定は不要。
ヘッダー・キャッシュ Accept: application/jsonをリクエスト例に使用する。API-001の200・500応答にCache-Control: no-storeを付け、応答時点のdisplayed_atが古いキャッシュから再利用されないようにする。
認証・認可 認証なし。Authorizationヘッダーやログイン状態を取得条件にしない。今回の閲覧処理に認証由来の401・403は定義しない。
日時・数値・ID post_idと各件数はJSONの数値（整数）。件数は0以上。posted_atは時差情報付きISO 8601文字列。displayed_atは計算済みの表示文字列。日本国内向けとし、日付表示はAsia/Tokyo（JST、UTC+09:00）を使用する。
必須・null・空文字 正常応答の各投稿は8項目すべて必須・null不可。author・bodyはDBで空文字と指定した空白だけの値を禁止する。文字数上限は設けない。空白の定義とシード時の検証はDB設計TBL-001に従い、APIは保存された文字列を返す。
取得範囲・並び順 投稿テーブルの全件をposted_at降順、同日時はpost_id降順で取得する。フィルター・limit・offset・カーソル・ページネーション・追加読み込みは定義しない。同じ投稿日時の場合はpost_idの降順とする。
入力検証 パス変数・クエリ・ボディの入力項目はない。検索・並び替え条件をリクエストで指定しない。未定義のクエリは無視し、取得結果を変更しない。クライアントは送信しない。
副作用・重複呼出・制限 閲覧APIは参照のみ。INSERT・UPDATE・DELETEやシード投入を実行しない。再度呼び出しても投稿・件数は変更しない。フロントエンドの取得タイムアウトは5秒。自動再試行は行わず、失敗時に手動の再試行ボタンを提供する。レート制限は未採用。
ブラウザからの呼び出し 開発環境では同一オリジンの /api/posts をVite経由で呼ぶ。ブラウザから別オリジンのバックエンドへ直接接続する方式や追加CORS設定は今回採用しない。本番の構成は未決。
互換性 応答のラッパーは追加しない。属性・型を変更する場合はAPI・ロジック・入出力設計の対応箇所とJSON例を同時に更新する。今後の互換性維持・バージョン移行方針は未決。

3. API個別仕様

API-001：投稿一覧取得

設計項目 仕様
目的・関連 SCR-001（/）のITEM-003に表示する投稿を返す。内部処理はPRC-002、返却データはPost（CLS-001）。
メソッド・パス ブラウザ：GET /api/posts。バックエンド：GET /posts。認証なし。
共通仕様との差分 なし。2章の仕様を適用する。

リクエスト

区分 項目 必須・形式 仕様
パス変数 なし 対象外 全投稿が対象。
クエリ なし 対象外 条件指定なし。
ヘッダー Accept 任意・application/json JSON応答を受け取る。Authorizationは不要。
ボディ なし 対象外 リクエストJSONは送信しない。

リクエスト例

GET /api/posts HTTP/1.1
Host: 127.0.0.1:5173
Accept: application/json

成功レスポンス

設計項目 仕様
HTTPステータス 200 OK。0件でも200とする。204や404にはしない。
ヘッダー Content-Type: application/json
Cache-Control: no-store
ボディ Postの8属性を持つオブジェクトの配列。items・data・totalなどのラッパーや付加項目は設けない。全件をposted_at降順、同日時はpost_id降順で返し、0件なら[]。
項目名 JSONの型 必須・null 内容 サンプル値
post_id number（整数） 必須・null不可 投稿1件の識別子。 1
author string 必須・null不可 投稿者の表示名。関連Userオブジェクトを含めない。 ユーザーA
body string 必須・null不可 投稿本文。改行はJSON文字列内で表現する。 サンプルの投稿です。
posted_at string（ISO 8601） 必須・null不可 投稿日時。UTCのZまたは時差オフセットを持つ。クラスではdatetime。 2026-10-20T12:00:00+00:00
reply_count number（整数） 必須・null不可 リプライ数。0以上のシード値。 2
retweet_count number（整数） 必須・null不可 リツイート数。0以上のシード値。 1
like_count number（整数） 必須・null不可 いいね数。0以上のシード値。 5
displayed_at string 必須・null不可 posted_atと応答処理時の現在時刻からAPIが算出する。DBには保存しない。 2日

属性の元定義は 6章のPost属性一覧 を参照する。displayed_atは 14章の算出ルール に従い、1分未満は「たった今」、1時間未満は「○分」、1日未満は「○時間」、1週間未満は「○日」、1週間以上は「yyyy/mm/dd」とする。同じ応答では現在時刻を1回取得して全投稿に使用する。1週間以上の場合はposted_atをAsia/Tokyoへ変換してyyyy/mm/ddに整形する。

取得失敗

DB参照・Post生成・表示日時算出・JSON変換の失敗、および未来のposted_atの検出は、 ERR-001 に対応するHTTP 500を返す。途中まで生成した一覧を成功応答として返さず、空配列にも置き換えない。

取得した投稿にposted_at > nowの行が1件でもあれば、一覧取得全体をHTTP 500・POST_LIST_FETCH_FAILEDとする。未来の投稿を除外した部分一覧を返したり、「たった今」に補正したりしない。posted_at == nowは正常とし「たった今」を返す。日時の比較は時差を考慮した同じ時間軸で行う。

副作用と失敗時の状態

取得の成功・失敗のどちらもDBの投稿や件数を変更しない。通信断などで応答を受け取れなかった場合、クライアントは取得失敗として扱うが、APIの500応答を受信したとはみなさない。画面の状態管理・復旧導線は入出力・ロジック設計を参照する。

確認観点（自動テスト・画面操作で確認）

追加確認：同一posted_atの投稿を複数用意しpost_idの大きい順となること。1週間以上前の2026-10-01T18:00:00+00:00は日本時間で2026/10/02と表示されること。posted_atがnowと等しい場合は正常、わずかでも未来なら一覧全体が500となることを確認する。

ケース 期待する結果

0件 200、[]。取得失敗と区別できる。
認証なし Authorizationやログインなしで取得できる。
型・値 全8項目が必須・null不可。IDと件数は整数、各件数は0以上、posted_atは時差情報付き日時文字列。
本文 改行を含む本文がJSONとして正しく復元できる。
表示日時の境界 59秒/60秒、3599秒/3600秒、86399秒/86400秒、604799秒/604800秒で規則どおりに切り替わる。
DB・変換失敗 500と固定のcode・message。空配列・部分一覧を成功応答として返さず内部情報を含めない。
ヘッダー・再取得 200・500ともJSONとno-store。再取得で応答時点のdisplayed_atを算出する。
副作用 API呼出の前後で投稿・各件数が変わらず、シードが追加されない。
転送経路 ブラウザの/api/postsがバックエンドの/postsに転送される。

4. エラー仕様

この章はAPI-001のサーバー側取得失敗を定義する。項目入力がないため、項目単位の入力エラーは今回定義しない。追跡IDの採用は未決であり、現在の応答には含めない。

応答項目 型 必須・null 値・意味
code string 必須・null不可 POST_LIST_FETCH_FAILED。機械的に識別する固定コード。
message string 必須・null不可 投稿一覧を取得できませんでした。利用者向けの固定文言。
エラーID コード・HTTPステータス 発生条件・関連処理 返却・復旧方針
ERR-001 POST_LIST_FETCH_FAILED / 500 Internal Server Error API-001 / PRC-002。DB参照・Post生成・表示日時算出・JSON変換の失敗。posted_atがAPI処理で1回取得した現在時刻nowを超える場合もERR-001とする。LOG-001は出力候補。 内部例外・SQL・接続情報は返さない。原因解消後の再取得は可能。自動再試行は行わず、画面の再試行ボタンで新しい要求を開始する。

エラーレスポンス例

500 Internal Server Error。Content-Type: application/json、Cache-Control: no-store。 

{
  "code": "POST_LIST_FETCH_FAILED",
  "message": "投稿一覧を取得できませんでした。"
}

HTTP通信失敗など、レスポンス自体を受信できない場合はこのJSONを受け取れる保証はない。クライアント側の通信失敗と、サーバーが返したERR-001を区別する。
