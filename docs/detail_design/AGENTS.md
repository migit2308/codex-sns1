# 詳細設計書の作成・編集方針

## 適用範囲

- このディレクトリ以下の詳細設計書に適用する。リポジトリルートの `AGENTS.md` も参照する。
- 設計書はHTMLで作成し、ブラウザで閲覧できるようにする。
- ファイル名・本文は日本語を使用してよい。既存の命名に合わせる。
- 既存の `入出力設計.html` を構成・見た目の基準とする。

## HTML・デザイン

- 目次を用意し、ページ内リンクで各章へ移動できるようにする。各章には目次へ戻るリンクを設ける。
- 白地に紺色系の見出し、控えめな罫線を使用し、読みやすい仕様書らしいデザインにする。
- 見出しの階層、章番号、表のスタイルを揃える。
- 表と図を中心に、項目同士の対応が分かる構成にする。
- 外部ライブラリやCDNに依存せず、HTMLファイル単体で表示できるようにする。スタイルはHTML内に記述し、図にはSVGやHTML/CSSを使用する。
- 狭い画面でも閲覧できるようにする。幅の広い表や図は必要に応じて横スクロールを設ける。
- 印刷用のスタイルを用意し、目次の固定配置や表の幅などを調整する。
- 文書の言語、見出し、表の見出しセル、図の説明、キーボード操作時のフォーカス表示に配慮する。

## 記入・更新ルール

- テンプレートの記入欄は `［記入：内容の説明］` の形式で示す。
- 未確定の内容は「未決」、対象に含めない内容は「対象外」と記載する。推測で仕様を確定しない。
- 見本の画面名・操作・配置は、確定した仕様と誤解されないように「記入例」「未確定」などと明示する。
- 文書バージョン、更新日、作成者、ステータスの記入欄を設け、確定している情報だけを反映する。
- 画面ID（例：`SCR-001`）、共通部位ID（例：`COM-001`）、項目ID（例：`ITEM-001`）で、表と図を対応づける。例示の番号を実際の仕様と取り違えない。
- 画面や項目を追加・変更した場合は、一覧表、遷移図、レイアウト図、入力設計の関連箇所も更新する。
- HTMLの `id` は文書内で一意にし、複製時にはリンク先も合わせて変更する。

## 入出力設計書の構成

`入出力設計.html` は、次の6項目を基本構成とする。

| 章 | 項目 | 記載する内容 |
| --- | --- | --- |
| 1 | 画面一覧表 | 画面ID、画面名、URLパス、目的・表示内容、利用条件、備考 |
| 2 | 画面遷移図 | 画面間の移動方向、操作、遷移条件、引き継ぐ情報、失敗・中断時の動作 |
| 3 | 画面共通部位一覧表 | 共通部位ID、部位名、役割・表示内容、適用画面、表示・操作条件 |
| 4 | 画面共通設計 | 共通レイアウト、画面幅への対応、表示形式、処理中・空・エラー時の表示、入力・権限・キーボード操作の共通ルール |
| 5 | 画面レイアウト図 | 画面ごとの配置図、番号付きの要素一覧、表示内容・取得元、操作・表示条件、画面固有の補足 |
| 6 | 画面入力設計 | 画面ごとの入力形式、必須条件、初期値、入力制約、エラー表示、入力チェック・送信・キャンセル時の動作 |

- 画面遷移図は箱と矢印で表し、矢印に操作や条件を記載する。図で表しきれない条件は表で補足する。
- レイアウト図は配置と役割を示すワイヤーフレームとし、図中番号を要素一覧に対応づける。
- 個別画面のレイアウト・入力設計は、画面単位で追加する。
- 入力制約は上限値だけでなく、文字数の数え方、空白・改行の扱い、チェックのタイミングも明記する。

## データベース設計書の構成

`データベース設計.html` は、次の9項目を基本構成とする。見た目と目次の構成は `入出力設計.html` に揃える。

| 章 | 項目 | 記載する内容 |
| --- | --- | --- |
| 1 | ボリューム一覧表 | テーブル・ファイルの初期件数と容量、日次増加量、平均サイズ、予測時点の件数と容量、保存期間、算定根拠 |
| 2 | データベース設定 | 製品・バージョン、環境・構成、データベース・スキーマ名、文字コード・照合順序、タイムゾーン、設定値と理由・適用方法、接続・権限・運用方針 |
| 3 | テーブル一覧 | テーブルID、論理名、物理名・スキーマ、目的・保持する情報、主キー、関連テーブル |
| 4 | インデックス一覧表 | インデックスID・物理名、対象テーブル、列と並び順、種別・一意性、条件・付加列、利用目的、関連制約 |
| 5 | ER図 | テーブル間の関係、主キー・外部キー、参照元と参照先、多重度・必須性、更新・削除時の動作 |
| 6 | テーブルレイアウト図 | テーブルごとのカラム構成、論理名・物理名、型・長さ・精度、NULL許可、デフォルト・採番、キー・制約、データ保持・削除方針 |
| 7 | CRUD図 | 処理とテーブルの対応、関連する画面・API、作成・参照・更新・削除の種別、トランザクション範囲 |
| 8 | ファイル一覧 | ファイルID、名称・用途、形式・文字コード、保存先・関連テーブル、生成元・利用先、管理仕様への参照 |
| 9 | ファイル管理 | ファイルごとの保存先・命名規則、関連データとの対応、受け入れ条件、生成・更新・参照権限、保存期間・削除、失敗時の処理、バックアップ・監視 |

- テーブルID（例：`TBL-001`）、インデックスID（例：`IDX-001`）、関連ID（例：`REL-001`）、処理ID（例：`PRC-001`）、ファイルID（例：`FIL-001`）を表と図で揃える。
- テーブル・カラム・関連を変更した場合は、テーブル一覧、インデックス一覧、ER図、テーブルレイアウト、CRUD図などの関連箇所も更新する。
- 製品やバージョン、設定値、テーブル構成は推測で決めない。製品依存のデータ型や採番方式も、決定するまでは記入欄または「未決」とする。
- ボリュームには、基準日・予測期間・利用規模・サイズの単位・計算式を明記する。データ本体とインデックス・ログ・バックアップの容量は区別する。
- ER図の見本は仮のテーブル名・列名・関係であることを明示する。PK（主キー）、FK（外部キー）、多重度の記号には説明を添える。
- テーブルレイアウトはテーブル単位、ファイル管理はファイル種別単位で追加する。複合キーやテーブル単位の制約も記載する。
- CRUD図は処理を行、テーブルを列とする表で表現する。C＝作成、R＝参照、U＝更新、D＝削除の凡例を設け、論理削除などの記号の運用ルールを明記する。
- ファイルを使用しない場合は「対象外」と記載する。
- パスワードや秘密情報を含む接続文字列は記載せず、管理方法や設定名への参照を記載する。

## ロジック設計書の構成

`ロジック設計.html` は、次の16項目を基本構成とする。見た目と目次の構成は `入出力設計.html` に揃える。

| 章 | 項目 | 種類 | 記載する内容 |
| --- | --- | --- | --- |
| 1 | 機能一覧 | 管理系 | 機能ID、分類・機能名、目的、利用者・起動条件、関連する画面・処理、採用状況 |
| 2 | プログラム一覧 | 管理系 | プログラムID、名称・責務、ファイルパス・実行単位、関連機能、入出力・依存先、処理仕様への参照 |
| 3 | クラス一覧 | 管理系 | クラスID、名称・所属、責務、主要な属性・操作、関連プログラム、採用状況 |
| 4 | ユースケース図 | 個別系 | 利用者、システム境界、達成する目的、事前・事後条件、基本・代替・例外シナリオ |
| 5 | アクティビティ図 | 個別系 | 作業の流れ、担当者、開始・終了条件、分岐条件、例外 |
| 6 | クラス図 | 俯瞰系 | クラスの属性・操作・型・可視性、クラス間の関連・依存・継承、多重度・制約 |
| 7 | パッケージ図 | 俯瞰系 | クラス・モジュールのまとまり、責務、公開する機能、依存方向と理由 |
| 8 | シーケンス図 | 個別系 | 処理の参加者、時系列の呼び出し・応答、引数・戻り値、分岐・例外、トランザクション |
| 9 | 処理フロー図（フローチャート） | 個別系 | 個別処理の実行順序、判定、繰り返し、終了・復帰先、正常・異常時の戻り値 |
| 10 | データフロー図（DFD） | 個別系 | データの発生元、処理、保存先、受け渡すデータ名・形式、関連テーブル・ファイル |
| 11 | 状態遷移設計 | 個別系 | 対象の状態、イベント・条件、遷移先、実行処理、許可しない遷移時の扱い |
| 12 | バッチ全体設計 | 俯瞰系 | 起動から終了までの流れ、スケジュール・依存関係、同時実行・再実行、失敗・復旧 |
| 13 | バッチプログラム一覧 | 管理系 | バッチID、関連プログラム・機能、起動契機・実行順、入出力、終了コード、再実行条件 |
| 14 | 処理設計（プログラム仕様書） | 個別系 | 処理ごとの目的・起動条件、入出力、手順、データ操作・整合性、例外・再試行、ログ・エラー、完了条件 |
| 15 | ログ一覧 | 管理系 | ログID、用途、出力する処理・条件、レベル・出力先、メッセージ・項目、保存・マスキング方針 |
| 16 | エラーコード一覧 | 管理系 | エラーID・コード、意味・発生条件、関連処理・ログ、返却・表示文言、通信ステータス・再試行可否、復旧方法 |

- 管理系は一覧による管理、俯瞰系は全体の構造、個別系は機能や処理の詳細を扱う。
- 機能（`FUN`）、プログラム（`PRG`）、クラス（`CLS`）、ユースケース（`UC`）、アクティビティ（`ACT`）、パッケージ（`PKG`）、データフロー（`DF`）、バッチ（`BAT`）、処理（`PRC`）、ログ（`LOG`）、エラー（`ERR`）のIDを関連する表と図で揃える。
- 入出力設計・データベース設計の画面ID、テーブルID、ファイルIDと対応づける。処理や依存関係を変更した場合は、関連する一覧・図・処理仕様も更新する。
- クラスやバッチなどの採用方式は推測で決めない。全項目の実装を必須とせず、未確定は「未決」、採用しない項目は「対象外」と記載する。
- ユースケース、アクティビティ、クラス、パッケージ、シーケンス、処理フロー、DFD、状態遷移、バッチ全体の図に記入例を設ける。見本の名称・関係・条件は仮のものであることを明示する。
- 図には記号・線・矢印の意味を添える。図で表しきれない条件・例外は表で補足し、SVGにはタイトルと説明を付ける。
- DFDではデータの流れを扱い、処理順序や分岐の詳細は処理フロー図・処理設計に記載する。状態遷移では対象データの状態を扱い、画面遷移と区別する。
- 処理設計は処理単位で追加し、正常系・境界値・異常系の確認観点を記載する。
- 目次が長い場合は、狭い画面・印刷での閲覧に配慮しつつ、目次全体へアクセスできるようにする。
- ログには秘密情報や不要な個人情報を含めない。エラー文言は内部向けと利用者向けを区別する。

## API設計書の構成

`API設計.html` は、次の5項目を基本構成とする。見た目と目次の構成は `入出力設計.html` に揃える。

| 章 | 項目 | 記載する内容 |
| --- | --- | --- |
| 1 | API一覧 | API ID、名称・目的、HTTPメソッド、パス、認証・権限、関連画面・処理、状態 |
| 2 | 共通仕様 | 環境・ベースURL、バージョン・命名、通信・データ形式、ヘッダー、認証・認可、日時・数値・ID、未指定・null・空文字、ページネーション、検索・並び順、入力検証、制限・重複送信・競合、ブラウザからの呼び出し、互換性 |
| 3 | API個別仕様 | APIごとの目的・メソッド・パス・条件、共通仕様との差分、リクエスト、成功レスポンス、エラー、JSON例、副作用・失敗時の状態、確認観点 |
| 4 | エラー仕様 | 共通のエラー応答構造、項目単位のエラー、利用者向け文言、追跡用ID、エラーコードとHTTPステータスの対応、再試行条件 |
| 5 | 未決事項 | 未決事項ID、内容、対象・影響、確認事項・候補、担当・期限、決定内容・反映先 |

- API ID（例：`API-001`）を一覧・個別仕様・エラー仕様で揃え、画面ID（`SCR`）・処理ID（`PRC`）に対応づける。
- API個別仕様はAPI単位で追加する。複製時はHTMLの `id`、API ID、一覧のリンク先も更新する。
- API設計ではHTTPでの受け渡しを定義する。画面での表示・操作は入出力設計、内部手順・トランザクションの詳細はロジック設計、保存構造はデータベース設計を参照し、重複を抑える。
- リクエストはパス・クエリ・ヘッダー・ボディを区別し、項目名、型・形式、必須条件、null許可、既定値、制約、例を記載する。
- 成功レスポンスにはHTTPステータス・ヘッダー・ボディを記載し、項目の型・出現条件・null許可・値の意味を明記する。ボディを返さない場合も条件を記載する。
- エラーコードの意味はロジック設計のエラーコード一覧で管理する。API設計では発生条件、HTTPステータス、返却内容、再試行条件を対応づける。正式なコードを追加する際は関連する一覧も更新する。
- リクエスト・成功レスポンス・エラーレスポンスのJSON例を設ける。仮の項目名・構造・値であることを明示し、正式な仕様に置き換えた後は項目表と一致させる。
- APIの方式、認証、パス、制限値、応答形式は推測で決めない。秘密情報の実値は記載せず、設定名や管理方法を記載する。
- 個別APIの確認観点には、正常系・境界値・入力不正・認証・権限・対象なし・競合など、対象となる条件を記載する。

## 編集後の確認

- 目次・参照リンクの移動先が存在し、意図した章や画面へ移動できることを確認する。
- タグの対応、HTMLの `id` の重複、表と図のID・番号の不整合がないか確認する。
- 他の設計書へのリンクは、ファイルと移動先の両方が存在することを確認する。JSON例を編集した場合はJSON構文も確認する。
- 見た目を変更した場合は、可能な範囲でブラウザ表示を確認する。狭い画面や印刷への影響も確認する。
- 実施した確認と、確認できていない事項を区別して報告する。
